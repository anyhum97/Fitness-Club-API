# Заметки о решении

Что сделано относительно исходного проекта (выданного вместе с [ЗАДАНИЕ.md](ЗАДАНИЕ.md)), какие
технические решения приняты и почему, что осталось за рамками.

Источник решения в таблицах:

- **ЗАДАНИЕ** — прямо требуется текстом задания;
- **уточнено работодателем** — подтверждено ответом на вопросы (раздел «Уточнения контракта от
  работодателя» в конце [ЗАДАНИЕ.md](ЗАДАНИЕ.md));
- **наше решение** — контракт молчит, выбран вариант исполнителя; в коде помечено `// решение:`;
- **по просьбе заказчика** — пожелание, высказанное по ходу работы.

### Инфраструктура

| Область | Как было | Что сделано | Почему | Источник |
|---|---|---|---|---|
| Логирование | стандартный логгер Microsoft, консоль, одна запись в коде — о необработанном исключении | Serilog: консоль и файл `WebApi/logs/webapi-<дата>.log` с ротацией по дням (14 файлов); уровни Debug / Information / Warning / Error; в каждой записи `TraceId`, `UserId`, метод и путь; итоговая строка на каждый запрос | Разбор инцидентов по заявке клиента | по просьбе заказчика |

### Общие правила API

| Область | Как было | Что сделано | Почему | Источник |
|---|---|---|---|---|
| Гонки | — | Каждая операция с местами или посещениями — одна транзакция с `SELECT … FOR UPDATE` строки занятия, затем абонементов; при взаимной блокировке до трёх попыток | Места не уходят сверх вместимости, посещения — в минус, одна бронь не списывается дважды | ЗАДАНИЕ |
| Ключ идемпотентности | — | Действует в пределах пользователя и эндпоинта; тот же ключ с другим телом — `409 idempotency-key-conflict`; хранятся только успешные ответы; повтор отдаёт `201` и тело первого ответа | Отказ не должен «запоминаться», чтобы его можно было повторить | ЗАДАНИЕ, наше решение |
| Ограничение частоты | — | 60 запросов в минуту на пользователя, фиксированное окно, счётчик в Redis; считаются все авторизованные запросы к восьми эндпоинтам, `401` не считается | Простая и атомарная реализация | ЗАДАНИЕ, наше решение |
| Порядок проверок | — | `400` → `404` → `409`; для брони: `enrollment-cancelled`, `class-cancelled`, `class-started`, `pass-expired`, `pass-exhausted`, `capacity-exceeded`; для очереди: `class-cancelled`, `class-started`, `already-waiting`, `seats-exceed-capacity`, `seats-available`; для загруженности `403` раньше `400` | Детерминированный ответ при нескольких причинах | наше решение |
| Числа и идентификаторы | — | Нечисловое, дробное, за пределами типа — `400`; id `0` или отрицательный — `404` | Контракт: нечисловое — 400, числовое без записи — 404 | ЗАДАНИЕ |
| Пустой параметр запроса | — | `roomId=`, `limit=`, `continuationToken=` — `400`, а не «параметр не задан» | Пустое значение — не число и не токен | наше решение |
| Расписание | — | Пагинация по ключу (`startsAt`, `id`); токен привязан к `from`, `to`, `roomId`, при несовпадении — `400`; `limit` между страницами менять можно; дата без времени — полночь UTC | Нет дублей и пропусков при добавлении занятий | наше решение |
| Кэш карточки брони | — | Redis: отдельно бронь с занятием и абонемент клиента; обе записи сбрасываются после любой операции API, которая их меняет, включая списание у ожидающего при продвижении | Клиент видит актуальные значения после операций API | ЗАДАНИЕ, наше решение |

### Лист ожидания и брони

| Область | Что сделано | Источник |
|---|---|---|
| Освободилось меньше мест, чем нужно первому | Места получает первый в очереди, кому их хватает; тот, кому не хватило, остаётся на своей позиции. Место не теряется и не уходит дважды: продвижение в той же транзакции | уточнено работодателем (выбор варианта — наш) |
| Абонемент при постановке в очередь | Не проверяется; очередь мест не занимает и посещений не расходует, они списываются при превращении ожидания в бронь | уточнено работодателем |
| Абонемент не подходит в момент продвижения | Ожидающий пропускается и остаётся в очереди, отдельной причины отказа нет | наше решение |
| Что продвигает очередь | Отмена брони (обязательно) и уменьшение числа мест (допустимо) | уточнено работодателем |
| Правило двух часов | Только для отмены; уменьшение возвращает разницу всегда, в том числе при просроченном или исчерпанном абонементе | уточнено работодателем |
| Замеченный риск | Можно уменьшить бронь за несколько минут до начала и вернуть посещения. Работодатель подтвердил, что это осознанная сторона контракта | уточнено работодателем |
| Продвижение на отменённом или начавшемся занятии | Не выполняется: записаться на такое занятие нельзя | наше решение |
| Результат продвижения | Новая отдельная бронь, а не прибавка к имеющейся брони клиента | наше решение |
| Прямая запись при непустой очереди | Разрешена: контракт не требует проверять очередь при записи | наше решение |
| Мест в запросе больше вместимости | В очередь не ставим: `409 seats-exceed-capacity` | наше решение |
| Уход из очереди после продвижения | `409 waitlist-fulfilled`; бронь отменяется своим эндпоинтом | наше решение |

## Уточнения контракта от работодателя

Получены 09.10.2026, полный текст — в конце [ЗАДАНИЕ.md](ЗАДАНИЕ.md). Коротко:

1. Если освободилось меньше мест, чем нужно первому в очереди, допустимы и строгий порядок,
   и передача мест следующему. Выбор назвать в описании и пометить в коде; место не должно
   потеряться или уйти дважды.
2. Постановка в очередь — не бронь: мест не занимает, посещений не расходует. Абонемент
   расходуется, когда ожидание становится бронью; что делать с неподходящим абонементом,
   решает исполнитель.
3. Продвижение при отмене брони обязательно, при уменьшении мест — на усмотрение исполнителя.
4. Правило двух часов — только для отмены. Уменьшение всегда возвращает разницу. Возможность
   уменьшить бронь перед самым началом — осознанная сторона контракта.

## Логи и разбор инцидентов

- Уровни: **Debug** — ход операций (блокировка занятия, кэш попал или нет, просмотр очереди);
  **Information** — бизнес-события (бронь создана, изменена, отменена с возвратом, постановка
  и уход из очереди, продвижение, повтор по ключу идемпотентности) и итог каждого запроса;
  **Warning** — отказы `409`, превышение лимита, пропуск ожидающего, конфликт ключа, повтор
  транзакции; **Error** — необработанные исключения со стеком.
- По умолчанию пишется уровень Information и выше, в окружении Development — Debug и выше
  (`appsettings.Development.json`). Шум Microsoft и EF ограничен уровнем Warning.
- Как найти запрос клиента: взять `traceId` из тела ответа об ошибке или заголовок `X-Trace-Id`
  любого ответа и найти строки `trace=<traceId>` в `WebApi/logs/webapi-<дата>.log`.

## За рамками

- Старые записи ключей идемпотентности не удаляются; для прода нужна периодическая чистка.
- Между фиксацией транзакции и сбросом кэша есть короткое окно, в которое параллельное чтение
  может положить в кэш старое значение (до истечения TTL в 5 минут). Последовательный клиент
  всегда видит актуальные данные.
- Изменения в базе мимо API (например, отмена занятия клубом) кэш не сбрасывают — контракт
  этого не требует.
- Логи пишутся в локальный файл; для прода их стоит отправлять в централизованное хранилище
  (Seq, Elasticsearch и т. п.) — достаточно добавить sink в конфигурацию Serilog.
